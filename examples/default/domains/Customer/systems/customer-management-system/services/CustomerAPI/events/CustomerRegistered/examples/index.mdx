## 1. Publish a new customer

Publish the typical registration: a customer who completed sign-up and provided their name. Welcome emails and CRM sync consume this shape.

### Payload details

- `eventId` uniquely identifies this event; `occurredAt` records when the registration happened in UTC.
- `customer.customerId` identifies the customer; `customer.email` is the address they registered with.
- `customer.name` is the display name the customer entered.
- `customer.status` is `ACTIVE`.

### Using this example

Use this as the baseline when testing consumers. The welcome email should address the customer by name, and CRM sync should create a contact with all four fields.

The examples use a **fictional Acme Events SDK** to publish a payload matching the CustomerRegistered schema. The package names and publish methods are illustrative.

```java CustomerRegistered.java
import com.acme.events.EventsClient;
import java.util.List;
import java.util.Map;

      "eventId", "b03ca9b3-b869-84bc-d88f-24bc05cd4e2b",

        "email", "amara.okafor@example.com",
        "name", "Amara Okafor",
        "status", "ACTIVE"
      )
    ));
  }
}
```

## 2. Publish an email-only registration

Publish a registration where no name was provided. This shows the optional `name` field being absent.

### Payload details

- `customer.name` is omitted rather than sent as an empty string.
- The remaining fields match the new customer example.

### Using this example

Use this to check that consumers do not assume a display name exists. The welcome email should fall back to a generic greeting, and CRM sync should leave the name blank.

The examples use a **fictional Acme Events SDK** to publish a payload matching the CustomerRegistered schema. The package names and publish methods are illustrative.
