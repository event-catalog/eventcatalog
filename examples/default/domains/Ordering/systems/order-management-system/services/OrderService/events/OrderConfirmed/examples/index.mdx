## 1. Confirm a paid order

Confirm the ten-T-shirt bulk order after the payment is authorised and stock is reserved. Fulfilment, customer notifications and analytics treat this as the signal that the order can go ahead.

### Payload details

- `confirmationNumber` is the customer-facing reference in the `ORD-` plus eight digits format.
- `paymentAuthorizationId` and `inventoryReservationId` point to the secured payment and stock reservation.
- `total` is in integer minor units and `currency` is `GBP`.
- `confirmedAt` records when the order was confirmed, in UTC.

The confirmed total is **49,990 pence (£499.90)**: ten T-shirts at 4,999 pence each.

### Using this example

Use this to check that fulfilment starts only after confirmation, and that the confirmation email shows `confirmationNumber` rather than the internal `orderId`.

The examples use a **fictional Acme Events SDK** to publish a payload matching the OrderConfirmed schema. The package names and publish methods are illustrative.

  }
}

## 2. Confirm a free replacement order

Confirm a free replacement cap sent after the customer reported a damaged item. There is nothing to charge, so no payment is authorised.

### Payload details

- `total` is `0` and `paymentAuthorizationId` is omitted.
- `inventoryReservationId` is still present, because the replacement cap has to be reserved.
- `confirmationNumber`, `currency` and `confirmedAt` are required as usual.

### Using this example

Use this to check that consumers accept a zero total and do not expect `paymentAuthorizationId` on every confirmation. Finance projections should record the order without a matching payment.

The examples use a **fictional Acme Events SDK** to publish a payload matching the OrderConfirmed schema. The package names and publish methods are illustrative.
