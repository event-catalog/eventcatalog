## 1. Publish an active product

Publish a fully described product that goes straight on sale. Consumers such as search indexing, the storefront and pricing can use it to make the product visible immediately.

### Payload details

- `eventId` uniquely identifies this event; `occurredAt` records when the product was created in UTC.
- `product.productId` identifies the product; `product.sku` is the stock keeping unit used by inventory.
- `product.price` uses integer minor units; `product.currency` is `GBP`.
- `product.description` and `product.category` are present because the product is complete.
- `product.status` is `ACTIVE`, so the product is visible to customers.

### Using this example

Use this as the baseline when testing consumers. Search indexing should index it, and the storefront should show it at **4,999 pence (£49.99)**.

The examples use a **fictional Acme Events SDK** to publish a payload matching the ProductCreated schema. The package names and publish methods are illustrative.

```javascript product-created.js
  occurredAt: "2026-09-11T07:30:00Z",
  product: {

    sku: "SKU-TSHIRT-BLK-M",

    price: 4999,
    currency: "GBP",
    category: "apparel",
    status: "ACTIVE",
  },
});
```

## 2. Publish a draft product

Publish a product that has been created without a description or category and is not yet visible to customers. This shows the optional fields being absent.

### Payload details

- `product.description` and `product.category` are omitted rather than sent as empty strings.
- `product.status` is `DRAFT`, so the product must not be indexed or sold.
- The remaining fields match the active product example.

### Using this example

Use this to check that consumers tolerate missing optional fields and respect the `DRAFT` status. Search indexing must skip it, and the storefront must not show it.

The examples use a **fictional Acme Events SDK** to publish a payload matching the ProductCreated schema. The package names and publish methods are illustrative.
